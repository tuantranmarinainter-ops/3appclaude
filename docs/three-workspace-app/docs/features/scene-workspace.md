## Scene render jobs — DOC-041

`scene.render` snapshots the committed project, source revision and source SHA, then calls the existing offline Topview `renderFrames` path. Inputs permit at most nine unique frame-camera samples, three cameras and 1024×1024 output; one local job runs at a time. Progress updates per rendered frame. Job state is persisted under the project `.jobs` directory; only the ten most recent terminal jobs are retained. Cancellation closes the headless browser and removes partial output. `job.get` returns file IDs, names, sizes and SHA-256 values; the local file route rechecks the hash before returning bytes.

The real output directory remains in the client: Scene UI uses the user's browser-approved `FileSystemDirectoryHandle`; Python CLI and MCP use a folder explicitly supplied to that local client. The API receives only `{kind:"client-directory",id:UUID}`, stores rendered artifacts inside the project job area, and never receives or writes an absolute user path. UI/CLI/MCP write verified files into a separate `render-<jobId>` subfolder. MCP starts asynchronously and saves when a later `job.get` sees success. If its process restarts, the client must repeat `scene.render` with the same request ID and path to restore the local destination association.

Primitive Chromium rendering and cancellation, retry/idempotency, job status, hash-verified PNG download and history immutability are tested. Punch Combo FBX rendering also passes when the fixture is enabled. Two-camera browser OPFS saving passed. OS folder-picker writes, animated pose/render parity, texture/compression variants, broad-format behavior, live MCP host and game/Film acceptance remain unverified. See [DOC-041 evidence](../evidence/scene-render-jobs.yaml).

`prop.add` places any imported model asset as a Topview prop, including GLB/glTF models without a skin. It stores the existing content-addressed asset URL in the node and commits through shared revision/history; it does not create Character or Skeleton records. The unified asset rail exposes the action; CLI/MCP use the same command, and CLI can pass transform and an existing group parent. Full catalog/primitive/path workflows and scene-level acceptance remain partial.

The Python bridge exposes `scene apply PROJECT_ID operations.json`. The shared broker accepts batches of up to 64 `node.transform.patch`, `node.flags.set`, `node.rename`, `node.clone`, `node.reparent` and `node.delete` operations; `document.replace` remains a single-operation path. Every batch validates against a project snapshot and commits as one revision/history entry. Cloning reuses Topview's document duplication helper and copies descendant nodes, native motion/camera/path clips, FCurves and user keys; shared Character IDs and MotionBindings are remapped in the same transaction. Topview's own editor clone also retains those shared records when autosaved through `document.replace`. An optional transform delta offsets an API clone. Reparent currently supports static primitive nodes between root groups or the scene root, preserving world transform and group child references. It rejects animated nodes, nested group parents, singular/sheared transforms and other node types because the pinned Topview runtime only parents primitives. Node deletion recursively includes group children and Topview derived path nodes, removes dependent motion/path/camera clips and editorial shots, selects a fallback active camera, and reconciles Character, FCurve/user-key and MotionBinding records. It rejects locked nodes, invalid graphs, surviving camera references or Retarget sessions before commit. The existing Python CLI and MCP bridge forward this contract unchanged. Browser-level acceptance remains unimplemented.

## Effective-world camera subject sampling — DOC-039

Before camera bindings run, the frame evaluator can accept a non-wire resolver for subjects whose world transform depends on loaded skeletal motion. The project sampler preloads the referenced shared Character and Motion sources once, reuses `createSkeletonEvaluator` for each frame, and feeds the actor's world position and horizontal rotation into the existing Topview subject/look-at binding logic. The evaluator is disposed when sampling ends or the consumer cancels. Missing, unsupported, or mismatched source rigs fail before the first sample; no source asset or project revision is modified.

Validation: Builder 96 test files passed (553 passed, one existing skip); Builder source/test typechecks and build/finalize passed; Studio typecheck and targeted ESLint passed; camera command 1/1 and FBX import integration 12/12 passed with Punch Combo enabled. The integration compares every camera sample against the same frame's actor world matrix, including rotation-relative offset and the left endpoint. This verifies numeric CPU sampling, not visual camera framing, browser rendering, Film export, or game playback. See [DOC-039 evidence](../evidence/camera-subject-sampling.yaml).
